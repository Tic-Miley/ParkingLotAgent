# 工具体系需求边界设计理念

> 版本 1.0 | 2026-06-09 | 为什么二维聚合由 LLM 自行解决，而非纳入工具

---

## 一、不是"能不能"，而是"该不该"

从技术上看，把二维聚合纳入工具是可行的——加一个 `secondary_group_by` 参数即可。但这样做会引发三个连锁问题。

### 1.1 组合爆炸

现有 7 个 `group_by` 维度。如果支持二维交叉，C(7,2) = 21 种组合。每种组合的语义差异巨大：

| 组合 | 结果形态 | LLM 需要做的解读 |
|------|---------|----------------|
| date × vehicle_type | 面板时间序列 | 每条线代表一个类型，观察趋势分化 |
| floor × vehicle_type | 交叉表 | 每层哪种类型多，判断楼层偏好 |
| hour × day_of_week | 密度矩阵 | 哪个格子的值最高 = 高峰时刻 |
| floor × hour | 三维概念 | 需要热力图才能直观呈现 |

**如果工具封装了所有 21 种组合，工具的返回结构就不再统一**——有的适合画折线图，有的适合堆叠柱状图，有的适合热力图。工具返回一个通用的多维数组，LLM 还得再解析它、理解它、选择可视化方式。这和 LLM 直接写 SQL 的认知负担**完全等价**，但丧失了 SQL 的灵活性。

### 1.2 工具语义退化

一维聚合的语义是清晰的、处处一致的：

```
"按 X 分组，统计每个 X 的数量"  ← 无论 X 是什么，这个句式不变
```

二维聚合没有这种统一语义：

```
"按 X 和 Y 交叉，统计每个格子的数量" ← 但这张表意味着什么？
```

`date × vehicle_type` 的交叉表意味着"趋势的分化"，`floor × vehicle_type` 的交叉表意味着"空间偏好的差异"。同一种操作，不同组合承载的是不同的分析视角。用同一个工具处理所有这些视角，要么工具过于通用（退化成一个 SQL builder），要么工具描述过于冗长（21 种组合的说明）。

### 1.3 工具与 SQL 的等价性边界

当一个工具的参数复杂到：

```python
query_aggregation(
    group_by=["date", "vehicle_type"],  # 主维度
    secondary_aggregation="ratio",       # 计算每组的占比
    pivot=True,                          # 透视表输出
    ...
)
```

它本质上是在发明一种新的查询语言。而这种语言不可能比 SQL 更精确、更灵活、更广为人知。**工具的封装价值在参数超越"枚举选择"进入"组合构造"时归零。**

## 二、设计理念：工具画在"语义不变性"边界上

工具体系的设计遵循一个核心原则：

> **工具封装那些"操作模式不变，只有参数取值不同"的需求；SQL 覆盖那些"操作模式随参数组合而变化"的需求。**

### 2.1 一维聚合满足"操作模式不变"

```
操作模式：SELECT <dim>, COUNT(*) FROM vehicle_record WHERE <cond> GROUP BY <dim>
参数变化：dim ∈ {vehicle_type, floor, date, hour, day_of_week, month}
```

无论 dim 取哪个值，SQL 模板、索引利用、结果结构、LLM 的解读方式都是**同构**的。这是参数化的天然边界。

### 2.2 二维聚合不满足"操作模式不变"

```
操作模式：取决于组合本身
  date × type   → 时间序列面板，需要按 type 分面或画多条线
  floor × type  → 交叉表，需要关注行百分比还是列百分比
  hour × day    → 密度矩阵，需要热力图
```

不同组合要求不同的后续处理逻辑。如果工具无法决定后续处理，就不应该封装这一步——**把决策权还给 LLM**。

### 2.3 边界图示

```
需求复杂度
    │
    │  ┌──────────────────────────────┐
    │  │  窗口函数、递归CTE、          │
    │  │  多表JOIN、复杂子查询         │  ← sql_query（LLM 完全自主）
    │  ├──────────────────────────────┤
    │  │  二维交叉分组                 │  ← sql_query
    │  │  HAVING / ORDER BY LIMIT     │  ← sql_query
    │  ├──────────────────────────────┤  ─── 语义不变性边界
    │  │  一维聚合（7种 group_by）     │  ← query_aggregation
    │  │  当前状态 / 历史趋势          │
    │  ├──────────────────────────────┤
    │  │  个体查询                     │  ← get_vehicle
    │  │  元数据查询                   │  ← get_config
    │  └──────────────────────────────┘
    │
    └──────────────────────────────────── 需求频率
```

**边界画在一维聚合和二维聚合之间**——不是因为二维聚合技术上做不到，而是因为这个位置恰好是"操作模式从同构变为异构"的转折点。

## 三、更根本的哲学：工具是 LLM 的义肢，不是大脑

这一点最重要。

LLM 的核心能力是什么？**理解语义、构造查询、提炼洞察**。这是它最擅长的。

LLM 的盲区是什么？**访问外部世界、记住精确的 Schema、控制资源安全**。这是它做不到的。

工具体系的设计应该遵循：

### 3.1 LLM 擅长的 → 工具不应该抢

| LLM 擅长的事 | 工具策略 | 原因 |
|-------------|:------:|------|
| 把"各类型占比趋势"翻译成 SQL | 不封装 | LLM 写 SQL 和填工具参数是同等难度的，但 SQL 更灵活 |
| 决定用饼图还是折线图 | 不封装 | 这是语义理解，LLM 的核心价值 |
| 从数据中提炼"本月比上月增长15%" | 不封装 | 这是洞察，LLM 的核心价值 |
| 处理非常规分析路径 | 不封装 | 低频 + 异构 = SQL 更高效 |

### 3.2 LLM 不擅长的 → 工具必须做

| LLM 不擅长的事 | 工具策略 | 原因 |
|--------------|:------:|------|
| 打开数据库连接、执行查询 | 封装 | LLM 无法做 I/O |
| 安全控制（防注入、只读、超时） | 封装 | LLM 不感知运行时安全 |
| 知道准确的表名和字段名 | Schema 嵌入工具描述 | LLM 会猜错 |
| 计算派生指标（ratio、occupancy_rate） | 工具内置 | 减少 LLM 的计算错误 |
| 高频重复查询的一键执行 | 一维聚合工具 | 节省 reasoning token，降低出错率 |

### 3.3 核心判断

**工具的目标不是替代 LLM 的推理，而是消除 LLM 推理中的不确定性和重复劳动。**

- 一维聚合高频出现 + 参数空间有限 → 封装为工具，一个参数搞定，LLM 不需要写 SQL
- 二维聚合低频出现 + 每种组合语义不同 → 不封装，LLM 直接写 SQL，工具提供 Schema 防止字段名错误

如果反过来——把低频、语义异构的需求也封装成工具——结果是一个参数爆炸的"超级工具"，LLM 需要花更多 token 去理解这个工具的各种参数组合，最终效果反而不如让它写一行 SQL。

## 四、设计决策速查

| 决策 | 理由 |
|------|------|
| 一维聚合由工具覆盖 | 操作模式同构、高频、参数空间有限 |
| 二维聚合由 `sql_query` 覆盖 | 操作模式异构、低频、SQL 更灵活 |
| 子查询/窗口函数/HAVING 由 `sql_query` 覆盖 | 不可参数化枚举，SQL 是唯一合理表达方式 |
| 派生指标由工具内置计算 | 减少 LLM 算术错误，统一口径 |
| Schema 嵌入工具描述 | 消除 LLM 的字段名猜测，降低错误率 |
| 图表类型由 LLM 决策 | 语义理解是 LLM 的核心价值，不应被工具替代 |

---

## 五、总结

二维聚合由 `sql_query` 覆盖而非 `query_aggregation`，不是能力问题，是设计选择：

1. **组合爆炸**：21 种二维组合，语义各不相同，无法用统一的返回结构承载
2. **边界清晰**：一维聚合满足"操作模式不变"，二维不满足——这是封装价值的自然边界
3. **尊重 LLM**：把"构造查询"这件事还给 LLM——它本就擅长，工具只需要消除它的盲区（Schema 可见性、安全执行、错误恢复）
