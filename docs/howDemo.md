# 如何向领导证明：AI Agent 在真实查询庞大数据库

> 核心问题：领导可能怀疑系统是"假 Agent"——要么规则匹配返回预设答案，要么把整个数据库塞给 LLM。本文档提供系统化的证明方案。

---

## 1. 背景：什么叫"假 Agent"？

| 作弊方式 | 表现 | 本系统为什么不是 |
|----------|------|-----------------|
| **规则匹配** | "还剩多少车位"永远返回固定数字，因为代码里写死了 | 系统有 9 个通用工具，特别是 T8 `sql_query` 可执行任意只读 SQL，无法穷举所有问题 |
| **全量塞给 LLM** | 启动时把 18 万行拼成文本，每次对话附在 prompt 里 | 18 万行 ≈ 500-700 万 tokens，DeepSeek V4 窗口最大 1M，物理上装不下 |

本系统是真正的 **ReAct Agent**：LLM 只看到工具的 Schema（函数签名 + 描述），**从未见过数据库内容本身**。它必须像人类分析师一样——决定调哪个工具、传什么参数、看返回结果、再决定下一步。

---

## 2. 三个层次的证明

### 2.1 数据规模证明（"数据库确实大"）

最直接的证据：**让系统自己说出数据量**。

在前端界面问：

> "这个数据库里总共有多少条停车记录？日期范围是什么？"

Agent 会调用 `get_summary_stats`，返回类似：

```
总记录数: 182,347
日期范围: 2026-02-08 至 2026-06-07
当前在场: 643 辆
```

18 万条记录这个数字本身就封死了"全量塞给 LLM"的可能。向领导算一笔账：

| 项目 | 数值 |
|------|------|
| 数据库记录数 | ~18 万条 |
| 每条平均字符数 | ~80 字符 |
| 全量文本量 | ~1440 万字符 ≈ **500-700 万 tokens** |
| DeepSeek V4 最大上下文 | 1M tokens（128K 起步） |
| 单次全量传入成本 | 约 $1.5-2.5（prompt 费用） |
| 实际每次查询 prompt | 约 2000-5000 tokens（仅 Schema + 历史） |

**一句话结论：**

> "18 万条数据如果全塞给 AI，上下文窗口根本装不下，光传输费就要 2 美元一次。我们的系统是让 AI 像分析师一样，自己决定查什么、怎么查。"

---

### 2.2 工具调用可见性证明（"AI 真的在查数据库"）

前端已有 `ToolCallCard` 组件，会实时展示每一步工具调用。这是**最强的现场证据**。

```
用户：最近一个月停车数变化趋势？

  ✓ 查询停车趋势完成  [点击展开 → 看到 30 天的每日数据]
  ✓ 生成统计图表完成  [折线图渲染出来]
```

向领导演示时，**刻意点击展开 ToolCallCard**，让他看到：

- 工具名称（`get_trend`）
- 返回的真实数据结构（`entry_count: 1542, exit_count: 1498 ...`）
- 这些数字不可能被预设，因为每天数据都不同

如果领导追问"怎么证明数据不是假的"，追加一个**验证性问题**：

> "帮我查一下，2026 年 4 月 15 日入场了多少辆车？"

Agent 会用 `sql_query` 生成并执行：

```sql
SELECT COUNT(*) FROM vehicle_record
WHERE DATE(entry_time) = '2026-04-15'
```

这个日期是随意挑的，不可能被预设。返回合理的数字（1300-1700 之间）就证明了真实查询。

---

### 2.3 智能决策证明（"AI 不是简单调一个函数"）

这是最有说服力的。设计一个**需要多步推理 + 自定义 SQL** 的问题：

> "帮我分析一下：哪个楼层的新能源车占比最高？和整体占比对比如何？"

这个问题的复杂度在于：

1. 没有现成的工具能直接回答
2. Agent 必须拆解为多步

**Agent 的实际执行过程：**

```
✓ 查询楼层状态完成       → F1:182辆, F2:156辆, F3:171辆, F4:134辆
✓ 执行数据查询完成       → F1 新能源占比 38.5%
✓ 执行数据查询完成       → F2 新能源占比 44.2%
✓ 执行数据查询完成       → F3 新能源占比 41.8%
✓ 执行数据查询完成       → F4 新能源占比 47.1%
✓ 生成统计图表完成       → 柱状图：各楼层新能源占比对比
```

Agent 最终回答：

> "F4（4 楼）的新能源车占比最高，达到 47.1%，超出整体平均水平约 5 个百分点..."

领导在前端可以看到 **4-6 个 ToolCallCard 依次执行**，这就是 Agent 在"思考"和"行动"的完整轨迹。

## 3. 可准备的"证据包"

### 3.1 架构对比图

```
┌─ "假 Agent" ─────────────────────┐
│  用户问 → 关键词匹配 → 返回预设答案  │
│  或                                 │
│  用户问 → 全量 DB 塞进 context → LLM │
└──────────────────────────────────┘

┌─ 我们的系统 ────────────────────────────────┐
│  用户问 "还剩多少车位"                         │
│    ↓                                         │
│  LLM 看到 9 个工具的描述（未看到数据）           │
│    ↓                                         │
│  LLM 决定：调用 get_current_vacancy           │
│    ↓                                         │
│  SQLite 查询 → {occupied: 652, vacant: 148}  │
│    ↓                                         │
│  结果返回 LLM → LLM 综合生成回答                │
│    ↓                                         │
│  回答 + 图表 → 用户                            │
│                                              │
│  数据从未离开数据库，LLM 只看到按需查询的结果     │
└──────────────────────────────────────────────┘
```

### 3.2 关键数字

| 指标 | 数值 | 意义 |
|------|------|------|
| 数据库记录数 | ~18 万 | 规模远超 LLM 窗口 |
| 工具体系 | 7 业务 + 1 通用 SQL + 1 图表 = 9 个 | 覆盖范围宽，非规则可穷举 |
| Agent 最大迭代 | 8 轮 | 支持多步推理 |
| 单次查询 Token | ~3000-8000 | 全量传入的 1/1000 |
| LLM 决策 + 工具执行 | 2 步起 | 每一步都是真实查询 |

### 3.3 技术架构要点

- **ReAct 循环**：LLM 在工具决策阶段为非流式（保证 JSON 完整），文本响应阶段为流式（用户体验）
- **工具注册格式**：OpenAI Function Calling 兼容，与 DeepSeek V4 原生对接
- **安全约束**：sql_query 工具仅允许 SELECT，连接为只读模式，行数上限 1000
- **SSE 推送**：`tool_call` / `text` / `chart` / `done` 四种事件类型，前端实时渲染

## 4. 推荐演示脚本（5 分钟）

按顺序执行，层层递进：

| 步骤 | 用户输入 | 目的 | 看点 |
|------|---------|------|------|
| 1 | "数据库总共有多少条数据？" | 证明数据规模 | ToolCallCard 展示 18 万 |
| 2 | "现在还剩多少车位？" | 基础查询演示 | 文本回答 + 占用率图表 |
| 3 | "帮我查 2026 年 3 月 15 日进了多少车？" | 证明非预设 | Agent 用 `sql_query` 写自定义 SQL |
| 4 | "哪个楼层新能源车最多？" | 多步推理 | 看到 4-6 个工具调用依次执行 |
| 5 | 手动展开一个 ToolCallCard | 展示原始数据 | 领导看到真实的查询结果 |

---

## 5. 总结

证明的核心不是"数据库大"，而是**决策过程可见**。本系统已经具备所有技术基础：

- **SSE 推送工具调用状态**：前端实时展示每一步
- **ToolCallCard 组件**：可展开查看工具返回的真实数据
- **ReAct 循环**：LLM 决策 → 工具执行 → 结果反馈的完整链条

演示建议：

1. **刻意展示** ToolCallCard 的展开内容，而非让它们一闪而过
2. **设计验证性问题**（随机日期、非预设维度），证明 Agent 是"查"出来的而非"背"出来的
3. **准备一张架构对比图**，把"全量传入 vs 工具调用"的 token 差异算清楚

> **一句话：这个系统的价值不在于它回答了什么，而在于它必须像人一样去查询、推理、整合，才能给出答案。**
